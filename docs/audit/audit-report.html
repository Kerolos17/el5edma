كود الدخول الشخصي مخزّن كنص صريح + هاش SHA-256 بدون salt

CRITICALالمصادقة

عمود personal_code مخزّن plaintext في varchar(10) (راجع migration ..revert_personal_code_to_string.php)، وعمود البحث personal_code_hash هو sha256() بدون salt. الكود من 4 إلى 6 خانات فقط، أي فضاء صغير جداً قابل للكسر فوراً بجداول قوس قزح عند تسريب قاعدة البيانات. الأسوأ: personal_code ليس ضمن $hidden في موديل User (المخفي هو الهاش فقط)، فأي تسلسل للموديل (toArray/JSON) قد يكشف الكود الصريح.

الإصلاح: إزالة العمود الصريح أو تشفيره عند التخزين (encrypted cast + توسعة العمود)، استبدال SHA-256 بـ HMAC بـ pepper من APP_KEY لعمود البحث، إضافة personal_code إلى $hidden، زيادة طول الكود إلى 8+، وإضافة قفل بعد محاولات فاشلة (lockout) فوق الـ throttle الحالي 5/دقيقة. عرض الكود الصريح يقتصر على SuperAdmin فقط مع تسجيله في Audit Log.

صلاحية قنوات البث الخاصة تفشل في الاختبار

HIGHBroadcasting

اختبار ChannelAuthTest يُرجع 200 بدل 403/401 عند محاولة الوصول لقناة مستخدم آخر. منطق التفويض في routes/channels.php سليم ظاهرياً ((int)$user->id === (int)$id)، لكن الفشل يعني إما اختلال إعداد بيئة الاختبار أو أن البث غير مُفعّل فعلياً (BROADCAST_CONNECTION=log). يجب التأكد من السلوك الفعلي في الإنتاج.

الإصلاح: تثبيت إعداد bروكر بث حقيقي (Reverb/Pusher)، إصلاح الاختبار ليعكس الإنتاج، والتأكد أن الإشعارات الخاصة لا تتسرب بين المستخدمين.

البيانات الطبية والشخصية بدون تشفير عند التخزين

HIGHPII/PHI

ملفات طبية، حالة إعاقة، أدوية، طلبات صلاة، عناوين، وبيانات الأسرة تُخزَّن كنص عادي. التحكم في الوصول جيد (Policies + FileAccessController + مسار private.file محمي بـ auth)، لكن لا يوجد تشفير عند التخزين لأكثر الحقول حساسية.

الإصلاح: تطبيق encrypted cast على الحقول الطبية الأكثر حساسية، تسجيل وصول الملفات الطبية في Audit Log، وإضافة سياسة احتفاظ/حذف بيانات (data retention).

تأكيد ضبط الإنتاج النهائي

MEDIUMConfig

ملف .env.production مضبوط جيداً (APP_DEBUG=false, SESSION_SECURE_COOKIE=true). بيئة التطوير APP_DEBUG=true على http وهو طبيعي محلياً. يجب ضمان عدم نشر أي بيئة بـ debug مفعّل، وإضافة رؤوس أمان (HSTS, X-Frame-Options, CSP).

الإصلاح: Middleware لرؤوس الأمان + CSP بـ nonce، تفعيل SESSION_ENCRYPT، ومراجعة same_site لتكون strict حيث يمكن.

STRENGTH

لوحة المعلومات تنفّذ عدة استعلامات count مع whereHas متداخل

MEDIUMDashboard

في Livewire/WebApp/Dashboard.php تُحسب كل إحصائية باستعلام منفصل يستخدم whereHas('beneficiary') مع whereIn(select id). مقبول حالياً لكنه يتمدد خطياً مع نمو البيانات وعدد الأدوار.

الإصلاح: تجميع الإحصائيات في استعلام/استعلامين مع selectRaw aggregates، وتخزين نتائج اللوحة في الكاش لمدة قصيرة (60-300 ثانية) عبر CacheService الموجود.

Cache و Queue على File / Database في الإنتاج

MEDIUMInfra

CACHE_STORE=file و QUEUE_CONNECTION=database في الإنتاج. مقبول لحجم صغير، لكن predis مثبّت بالفعل، فالانتقال لـ Redis متاح بلا تكلفة كبيرة ويحسّن الإشعارات والطوابير والجلسات.

الإصلاح: نقل Cache + Queue + Session إلى Redis عند الإطلاق، وتشغيل عامل طابور (queue worker) دائم عبر supervisor/PM2.

33 اختبار فاشل تخفي أي regression جديد

HIGHCI

تتجمع الإخفاقات في فئات واضحة، وأغلبها انحراف بيئة اختبار بعد ترقية الإطار/Livewire وليست بالضرورة أعطالاً إنتاجية:

  • أخطاء CSRF (419) في اختبارات Controllers FcmToken / Locale / Registration لا تعطّل CSRF
  • assertSeeLivewire لم يعد موجوداً على Response AppShellTest يستخدم API قديم لـ Livewire v3
  • ChannelAuthTest (200 بدل 403) يحتاج تحقيق فعلي — أمني
  • CodeLoginControllerTest (redirect/last_login) قد يكون مرتبطاً بتغيير LoginResponse
الإصلاح: تصنيف كل فشل: إصلاح اختبار (CSRF/Livewire API) مقابل عطل حقيقي (Channel auth). الهدف: سويت خضراء 100% + بوابة CI تمنع الدمج عند أي فشل. الوصول لتغطية 80%+ الموثّقة كمعيار للفريق.
